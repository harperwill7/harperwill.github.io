## Artifacts and Enhancements

### Enhancement One: Software Design and Engineering

* **Artifact:** Thermostat.py
* **Description:** The artifact, Thermostat.py, is a Python program crafted to manage a functional Internet of Things (IoT) thermostat prototype that is built on a Raspberry Pi. This prototype incorporates a variety of hardware components, such as an AHT20 temperature/humidity sensor, a 16x2 character LCD, two PWM LEDs (Red for heating and Blue for cooling), along with three physical buttons, all connected through GPIO and I2C.
The code features a state machine with three distinct states: Off, Heat, and Cool. Its primary functions include reading the current temperature, allowing the user to modify a temperature setpoint, controlling the LEDs to visually represent the current state and whether the system is actively heating (with Red pulsing) or cooling (with Blue pulsing), displaying status information (date/time, current temperature, setpoint) on the LCD, and transmitting a comma-separated status string over the serial port (UART) every 30 seconds to an external TemperatureServer.

## Professional Self Assessment

I chose the Thermostat.py Python code for a Raspberry Pi based smart thermostat from CS 350: Emerging Systems Architecture and Technologies course, as it serves as a thorough example of embedded systems programming, object-oriented design, and concurrent programming. The artifact was enhanced by applying defensive programming principles. Setpoint Input Validation,  I established MIN_SETPOINT (60°F) and MAX_SETPOINT (85°F) constants and incorporated bounds checking into the processTempIncButton and processTempDecButton functions. This measure prevents users from setting unreasonable or unsafe temperatures, thereby boosting the system's robustness and reliability. Then Reliable Serial Communication Logic, I addressed a potential problem in the manageMyDisplay thread where the counter variable was being reset. By ensuring that the counter only resets when the 30-second serial message is successfully transmitted, I ensure that the status update is consistently sent every 30 seconds, which enhances the accuracy of system reporting. Finally, Code Maintainability, I implemented a SERIAL_PORT constant to replace the hardcoded string /dev/ttyS0 in the serial.Serial() initialization, adhering to best practices for configuration management. The improvement of the Thermostat.py artifact successfully aligns with the course outcome of demonstrating an ability to use well-founded and innovative techniques, skills, and tools in computing practices for the purpose of implementing computer solutions that deliver value and accomplish industry-specific goals. This was achieved by showcasing OOD principles in class design and the application of state machines, by connecting the Raspberry Pi GPIO/I2C with Python libraries for the sensor, display, and buttons, as well as by implementing threading to handle display and serial updates without hindering the main loop or button handlers. The improvement process highlighted the essential role of input validation in embedded systems. In a tangible device such as a thermostat, an extreme setpoint might result in mechanical degradation, energy inefficiency, or safety issues. Implementing the bounds check served as a valuable lesson in ensuring that the software is both safe and operational. Additionally, I acquired a more profound insight into managing a counter variable within a thread executing a time-based loop to guarantee precise timing for scheduled events (the 30-second serial update). The main difficulty lay in examining the timing logic within manageMyDisplay. The initial code setup reset the counter in a manner that functioned correctly only if the complete loop iteration lasted precisely one second. Yet, even a slight delay in other processes could disrupt the timing. Troubleshooting a time-sensitive problem in a concurrent thread demands meticulous consideration. By confining the counter = 1 reset to the if((counter % 30) == 0): block, I clarified the ambiguity and guaranteed that the 30-second interval is preserved accurately, irrespective of minor fluctuations in the loop.

I chose this artifact for my ePortfolio to demonstrate my capability to utilize advanced theoretical computer science principles—particularly data structures and algorithmic analysis—in addressing a concrete, real-world engineering challenge. The original element that revealed a flaw was the destination search function, which relied on slow, resource-heavy database operations (likely a Mongoose regex or $text index query). Although this initial method was straightforward to implement, it led to an inefficient O(N) time complexity (where N represents the number of trips), indicating that search latency would increase linearly with the size of the database. The enhancement I made, which involves constructing and querying an in-memory Trie (Prefix Tree), effectively highlights my expertise in algorithmic optimization and complexity management. The improvement effectively achieved the intended Course Outcome 3: To design and assess computing solutions that address a specific problem by utilizing algorithmic principles and adhering to computer science practices and standards relevant to the solution, while also considering the trade-offs associated with design decisions. By substituting the expensive database search with a tailored, in-memory Trie structure, the time complexity for destination prefix lookups was significantly reduced to O(L) (where L represents the length of the search query), resulting in almost instantaneous results. This illustrates my capability to assess design trade-offs, opting to allocate more server memory (for the Trie) in return for substantial enhancements in application speed and responsiveness. The journey of improving this artifact offered significant insights into full-stack integration and the timing of startups. One major takeaway was the critical need for a solid server initialization process. The Trie structure needs to be completely loaded from the database once the Mongoose connection is established, but prior to the server beginning to accept API requests. A significant challenge was making sure that this asynchronous initialization was properly managed in app.js to avoid the server launching with an empty Trie. This experience highlighted the necessity of a meticulous system startup sequence and effective dependency management for developing high-performance, production-ready services.

I chose to enhance the Travlr backend because it embodies a vital crossroads of contemporary web development expertise: API design, authentication, and database integrity. The booking feature is the most commercially sensitive aspect of the application, making it an ideal candidate to demonstrate advanced reliability and security capabilities. Key elements of the artifact that highlight my expertise include the implementation of a Mongoose Multi-Document Transaction within the tripsBookTrip controller function, which guarantees that the booking process is both atomic and dependable. Additionally, I refactored the API by establishing a dedicated, authenticated route (/trips/:tripCode/book) and seamlessly integrated the intricate transactional logic into a streamlined controller function. I also recognized that the original strategy of utilizing SQL Stored Procedures was not compatible with MongoDB, leading to a successful transition to Mongoose Sessions for managing transactions. Furthermore, it is confirmed that by employing Mongoose models along with its native query methods (such as Model.findOne), the code is inherently safeguarded against conventional SQL injection threats. The upgrade aimed to tackle two significant vulnerabilities in database interactions: race conditions/partial bookings and the risk of SQL injection. Initially, the strategy was to implement SQL stored procedures. However, after examining the current code, it was evident that the application operates on MongoDB. Consequently, the enhancement was restructured to ensure the same level of reliability using native MongoDB features. The most important learning experience involved adjusting the idea of an ACID transaction to fit the NoSQL framework of MongoDB. In a relational setting, this is accomplished through stored procedures and row-level locking (FOR UPDATE). In MongoDB, the counterpart necessitates grasping and accurately applying the Multi-Document Transaction API with Mongoose sessions. I learned the key distinctions between locking mechanisms in SQL and NoSQL settings. I learned how to correctly initialize, utilize, commit, and roll back a Mongoose session to ensure data integrity during multiple read/write operations within a single controller call. Additionally, I recognized the significance of identifying the technology stack early, as architectural solutions for reliability (such as stored procedures versus transactions) rely heavily on the underlying database. The main challenge was to guarantee that each read and write action within the try block was properly linked to the session (.session(session)). If a session parameter was overlooked, that operation would run outside the transaction, undermining atomicity and potentially leading to a race condition. Debugging the transaction logic necessitated meticulous observation of the database state to confirm that the rollback functioned correctly in the event of a failure.
