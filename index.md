## Artifacts and Enhancements

### Enhancement One: Software Design and Engineering

* **Artifact:** Thermostat.py
* **Description:** The artifact, Thermostat.py, is a Python program crafted to manage a functional Internet of Things (IoT) thermostat prototype that is built on a Raspberry Pi. This prototype incorporates a variety of hardware components, such as an AHT20 temperature/humidity sensor, a 16x2 character LCD, two PWM LEDs (Red for heating and Blue for cooling), along with three physical buttons, all connected through GPIO and I2C.
The code features a state machine with three distinct states: Off, Heat, and Cool. Its primary functions include reading the current temperature, allowing the user to modify a temperature setpoint, controlling the LEDs to visually represent the current state and whether the system is actively heating (with Red pulsing) or cooling (with Blue pulsing), displaying status information (date/time, current temperature, setpoint) on the LCD, and transmitting a comma-separated status string over the serial port (UART) every 30 seconds to an external TemperatureServer.

## Professional Self Assessment

I selected the Thermostat.py Python code for a Raspberry Pi-based smart thermostat from the CS 350: Emerging Systems Architecture and Technologies course because it exemplifies embedded systems programming, object-oriented design, and concurrent programming. The artifact was improved by incorporating defensive programming principles. For Setpoint Input Validation, I defined MIN_SETPOINT (60°F) and MAX_SETPOINT (85°F) constants and added bounds checking to the processTempIncButton and processTempDecButton functions. This approach prevents users from setting unreasonable or unsafe temperatures, thereby enhancing the system’s robustness and reliability. Next, regarding Reliable Serial Communication Logic, I tackled a potential issue in the manageMyDisplay thread where the counter variable was being reset. By ensuring that the counter only resets when the 30-second serial message is successfully transmitted, I guarantee that the status update is consistently sent every 30 seconds, which improves the accuracy of system reporting. Lastly, for Code Maintainability, I introduced a SERIAL_PORT constant to replace the hardcoded string /dev/ttyS0 in the serial.Serial() initialization, following best practices for configuration management. The enhancements made to the Thermostat.py artifact effectively align with the course outcome of demonstrating the ability to utilize well-founded and innovative techniques, skills, and tools in computing practices to implement computer solutions that provide value and achieve industry-specific objectives. This was accomplished by illustrating OOD principles in class design and applying state machines, connecting the Raspberry Pi GPIO/I2C with Python libraries for the sensor, display, and buttons, and implementing threading to manage display and serial updates without disrupting the main loop or button handlers. The enhancement process underscored the critical importance of input validation in embedded systems. For instance, in a physical device like a thermostat, an extreme setpoint could lead to mechanical wear, energy waste, or safety hazards. The implementation of bounds checking proved to be a significant lesson in ensuring that the software remains both safe and functional. Furthermore, I gained a deeper understanding of how to manage a counter variable within a thread that runs a time-based loop to ensure accurate timing for scheduled events (the 30-second serial update). The primary challenge was analyzing the timing logic within manageMyDisplay. The original code configuration reset the counter in a way that only worked correctly if the entire loop iteration took exactly one second. However, even a minor delay in other processes could throw off the timing. Diagnosing a time-sensitive issue in a concurrent thread requires careful attention. By restricting the counter = 1 reset to the if((counter % 30) == 0): block, I eliminated the confusion and ensured that the 30-second interval is maintained accurately, regardless of slight variations in the loop.

I selected the Travlr Webserver for my ePortfolio to showcase my ability to apply advanced theoretical computer science concepts—especially data structures and algorithmic analysis—in tackling a specific, real-world engineering problem. The initial component that exposed a flaw was the destination search function, which depended on slow, resource-intensive database operations (likely a Mongoose regex or $text index query). While this original approach was easy to implement, it resulted in an inefficient O(N) time complexity (where N denotes the number of trips), suggesting that search latency would grow linearly with the database size. The enhancement I implemented, which involves building and querying an in-memory Trie (Prefix Tree), effectively demonstrates my skills in algorithmic optimization and complexity management. This improvement successfully met the intended Course Outcome 3: To design and evaluate computing solutions that solve a specific issue by applying algorithmic principles and following computer science practices and standards relevant to the solution, while also taking into account the trade-offs linked to design choices. By replacing the costly database search with a customized, in-memory Trie structure, the time complexity for destination prefix lookups was dramatically decreased to O(L) (where L denotes the length of the search query), leading to nearly instantaneous results. This demonstrates my ability to evaluate design trade-offs, choosing to invest more server memory (for the Trie) in exchange for significant improvements in application speed and responsiveness. The process of enhancing this artifact provided valuable insights into full-stack integration and the timing of startups. A key takeaway was the essential requirement for a robust server initialization process. The Trie structure must be fully loaded from the database once the Mongoose connection is established, but before the server starts accepting API requests. A major challenge was ensuring that this asynchronous initialization was effectively handled in app.js to prevent the server from starting with an empty Trie. This experience underscored the importance of a careful system startup sequence and efficient dependency management for building high-performance, production-ready services.

I decided to improve the Travlr backend because it represents a crucial intersection of modern web development skills: API design, authentication, and database integrity. The booking feature stands out as the most commercially sensitive part of the application, making it a perfect example to showcase advanced reliability and security features. Key aspects of the project that demonstrate my skills include the implementation of a Mongoose Multi-Document Transaction within the tripsBookTrip controller function, ensuring that the booking process is both atomic and reliable. Moreover, I restructured the API by creating a dedicated, authenticated route (/trips/:tripCode/book) and smoothly integrated the complex transactional logic into a more efficient controller function. I also realized that the initial approach of using SQL Stored Procedures was incompatible with MongoDB, which led to a successful shift to Mongoose Sessions for transaction management. Additionally, it has been confirmed that by utilizing Mongoose models along with its native query methods (like Model.findOne), the code is inherently protected against typical SQL injection vulnerabilities. The upgrade was designed to address two major vulnerabilities in database interactions: race conditions/partial bookings and the threat of SQL injection. At first, the plan was to use SQL stored procedures. However, upon reviewing the existing code, it became clear that the application is built on MongoDB. As a result, the enhancement was redesigned to maintain the same level of reliability by utilizing native MongoDB features. A crucial learning moment was adapting the concept of an ACID transaction to align with MongoDB's NoSQL framework. In a relational database, this is achieved through stored procedures and row-level locking (FOR UPDATE). In MongoDB, the equivalent requires understanding and effectively using the Multi-Document Transaction API along with Mongoose sessions. I discovered the fundamental differences between locking mechanisms in SQL and NoSQL environments. I learned how to properly initialize, use, commit, and roll back a Mongoose session to maintain data integrity during multiple read/write operations within a single controller call. Furthermore, I acknowledged the importance of early identification of the technology stack, as architectural solutions for reliability (like stored procedures versus transactions) are heavily dependent on the underlying database. The primary challenge was ensuring that every read and write operation within the try block was correctly associated with the session (.session(session)). If a session parameter was missed, that operation would execute outside the transaction, jeopardizing atomicity and possibly resulting in a race condition. Debugging the transaction logic required careful monitoring of the database state to verify that the rollback function worked correctly in case of a failure.
